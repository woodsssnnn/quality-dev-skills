# 反模式

优化过程中的常见陷阱和正确做法。

## 反模式列表

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | 为了提分而增加规则 | 规则应该来自 best-practices，不是为了提分 |
| 2 | 优化后技能变长 | 优化应该是精炼，不是膨胀 |
| 3 | 忽略 val set 过拟合 | 每轮必须在 val set 上验证 |
| 4 | 改变目录结构 | Bounded edit 只改文本 |
| 5 | 添加时间敏感信息 | 技能内容不应包含日期、版本号等 |
| 6 | 嵌套引用过深 | 引用最多一层深 |
| 7 | 步骤之间没有明确边界 | 每个步骤有清晰的输入/输出 |
| 8 | 缺少 pass/fail 标准 | 每个 Gate 必须有量化标准 |
| 9 | 评估器规则过于严格 | 区分假阳性和真阳性 |
| 10 | 忽略 skill 内部引用 | 内部引用不计入深度检查 |

## 详细说明

### 1. 为了提分而增加规则

**反模式**: 发现某条规则没覆盖，临时加一条规则来提分

**正确做法**: 规则应该来自公认的 best-practices，不是为了提分而临时发明

### 2. 优化后技能变长

**反模式**: 优化后 SKILL.md 行数增加

**正确做法**: 优化应该是精炼，把详细内容移到 references/，主文件应该更简洁

### 3. 忽略 val set 过拟合

**反模式**: 只在 train set 上验证，不在 val set 上验证

**正确做法**: 每轮优化后必须在 val set 上验证，防止过拟合

### 4. 改变目录结构

**反模式**: 优化时增删文件、改文件名

**正确做法**: Bounded edit 只改文本内容，目录结构保持不变

### 5. 添加时间敏感信息

**反模式**: 在技能中写入具体日期、版本号

**正确做法**: 技能内容应该是时间无关的，用 "当前"、"最新" 等相对表述

### 6. 嵌套引用过深

**反模式**: references/sub1/sub2/file.md 这种多层结构

**正确做法**: 引用最多一层深，references/file.md

### 7. 步骤之间没有明确边界

**反模式**: 步骤描述模糊，没有清晰的输入/输出

**正确做法**: 每个步骤有明确的输入（从哪来）和输出（到哪去）

### 8. 缺少 pass/fail 标准

**反模式**: 只说 "优化到满意为止"，没有量化标准

**正确做法**: 每个 Gate 必须有量化标准，如 "score > 0.7 才通过"
